1. Project overview

Problem. Clinics must share sensitive health information between patients, doctors and administrators without trusting any network, user or component by default.

Roles. Patient (book, view prescriptions, upload records), Doctor (consultations, SOAP notes, e-prescriptions), Administrator (users, analytics, audit log).

Technology. Next.js 14 (React, Tailwind) · FastAPI (Python 3.11) · SQLAlchemy 2 + Alembic · PostgreSQL 16 · JWT + bcrypt · boto3 · Docker.

Why zero-trust and multi-tier matter in healthcare. Health records are among the most sensitive data. Separate network tiers (web, application, database) limit the damage of any single break-in; zero-trust adds explicit authentication and authorisation on every request, least privilege, encryption everywhere and a complete audit trail.

2. Application workflow

FlowSteps
BookingPatient chooses doctor and slot, API checks conflicts (HTTP 409 if taken), appointment and telemedicine room id are created, audit entry written, SQS message, Lambda, SNS notification
ConsultationDoctor opens the appointment, saves a SOAP note with ICD-10 and vitals (doctor must own the appointment), issues a signed e-prescription, patient reads it (ownership checked)
Record uploadPatient requests an upload URL, browser PUTs the file straight to S3 (KMS-encrypted, 15-minute URL), API stores metadata (the key must be inside the patient's own prefix), Lambda tags the object with SHA-256 and scan status
AuditLogins, bookings, notes, prescriptions, uploads and downloads are written to an append-only audit table (actor, action, resource, IP, user agent, time); administrators read it; the API has no route to edit or delete it

Verified end to end on the live site by scripts/e2e_cloud_test.py (section 12).

3. Architecture

Two architectures are shown. The built one runs today. The designed one is the full zero-trust target (Terraform in terraform/); parts are blocked in the Learner Lab (CloudFront) or too costly for the credit (NAT, ALB, WAF, Multi-AZ).

Trust boundaries

BoundaryControl
Internet to hostonly ports 80/443; TLS 1.3 via Caddy; security headers; no SSH
Host to databaseprivate subnets with no internet route; security group accepts only the application group; TLS enforced by RDS
Browser to S3presigned URL (15 min); bucket policy denies non-TLS; public access fully blocked
Application to AWSinstance role (IMDSv2, hop limit 2 for containers); no static keys in containers
SecretsSecrets Manager (KMS), fetched at application start; not in images, Git or the container environment

Why the frontend is a container, not S3 + CloudFront: the Next.js app is a Node server (next start), not a static export, and CloudFront is blocked in this account. Why no ALB/NAT: about USD 20 and 33 per month each (section 8); Caddy gives HTTPS and routing on the single host, and the free S3 gateway endpoint keeps S3 traffic off the internet.

VPC, subnets, route tables, security groups

Isolated network with three tiers. The public subnets hold the host; two private-db subnets hold RDS and have no internet route. The security groups form the chain internet, web SG (80/443), DB SG (5432 from the web SG only).

EC2 (Graviton), Docker and Systems Manager

One t4g.small host (IMDSv2 required, encrypted gp3 root volume) runs Caddy, Next.js and FastAPI in Docker (non-root, health-checked, logs to CloudWatch). Systems Manager gives shell access and remote commands without SSH.

ECR: private container registry

Stores the backend and frontend images. Tags are immutable, scan-on-push is on and images are KMS-encrypted; a lifecycle rule keeps the last 10.

RDS PostgreSQL

Private (no public address), KMS-encrypted, TLS enforced (rds.force_ssl), 7-day automated backups, deletion protection, logs exported to CloudWatch. Single-AZ by choice because Multi-AZ doubles the cost.

S3 medical-records vault

Documents are stored encrypted with the KMS key and versioned. The bucket is never public and is reached only through 15-minute presigned URLs issued after an authorisation check. A Lambda tags each upload.

KMS and Secrets Manager

One customer-managed key (rotation on) protects RDS, S3, secrets, EBS, SNS and CloudTrail. Three secrets hold the DB credentials, the JWT signing key and synthetic demo-user passwords. Values are never shown.

Cognito

User pool with groups patients, doctors, admins and optional TOTP MFA. Provisioned, but the running app uses its own JWT mode; end-to-end Cognito login is not verified.

SQS, SNS and Lambda

Booking events go to an SQS queue (with dead-letter queue), then the notifier Lambda, then SNS. Uploads trigger the document-scanner Lambda (SHA-256 plus a basic signature check; not an anti-malware engine).

CloudWatch and CloudTrail

Container logs stream to /carevia/app; eight alarms (host status, CPU, RDS CPU/storage/connections, application errors, DLQ, Lambda errors) notify an SNS topic; a dashboard shows the key metrics. CloudTrail records API activity (multi-region, log-file validation).

CloudFormation

Creates the three S3 buckets (workaround for the SCP).

11. SLA (summary)

The full SLA is the separate document Healthcare_Portal_SLA.pdf. In short: the weakest AWS commitments in the design are a single EC2 instance and single-AZ RDS (99.5 % class, about 3.65 h downtime per month), so the portal targets 99.5 % during clinic hours, RPO up to 5 minutes, RTO up to 20 minutes for a database restore and up to 5 minutes for a bad release. No long-term uptime has been measured yet. Multi-AZ RDS and a second instance behind a load balancer would raise the ceiling to 99.9 % or more (Designed-only).

13. Limitations and future work

  • Single AZ and single host: no tolerance for an AZ failure; add Multi-AZ RDS, a second instance and an ALB (designed).
  • The Learner-Lab role is broad: use least-privilege IAM roles in a normal account (Terraform provided).
  • CloudFront, WAF, GuardDuty, Config and Security Hub not built (blocked or costly).
  • Cognito is provisioned but not used by the app; MFA is not enforced in application mode.
  • CI/CD proof on GitHub is pending the repository push; Trivy and ECR scan results not yet captured.
  • Document files have no off-AWS backup; audit rows share the application database (use S3 Object Lock or a separate store).
  • Migration drift (missing indexes) and the in-memory rate limiter should be fixed for real use.

14. Conclusion

The portal runs online on AWS behind HTTPS, attached to a database, encrypted storage, secrets, messaging, monitoring and audit services, with infrastructure as code, a tested automatic rollback, a rehearsed database restore and measured performance. Before hosting, the audit found two critical and several high-severity flaws that would have made any deployment unsafe; they were fixed and verified on the live system. The honest limits (single AZ, lab role, untested WebRTC and Cognito, pending GitHub pipeline proof) are listed so that the next step, a normal account with the full designed architecture, is clear.
